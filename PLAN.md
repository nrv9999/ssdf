Зафиксировано 2026-11-23. Раздел «Кандидаты» — на рассмотрение пользователя, не утверждён.

## Принято

1. **Настройка имени БД — единая для SQL и Python.**
   В Python уже вынесено в `--dbname` (дефолт `demo`). В SQL `demo` зашито в connstr dblink
   (`df.exec_flow`, `df.exec_batch_from_id`). Настройку кладём в таблицу **`dh.setting(settng, value)`**
   (схема `dh` — подтверждено пользователем). Оба пути читают дефолт оттуда.
2. **`max_parallel_points`** (дефолт **4**) — ограничение числа одновременно запущенных точек;
   если уперлись — ждём. **`max_parallel_points_polling`** (дефолт **5**, значение в секундах) —
   период поллинга ограничения. Настройки — в той же таблице. Заменяет стабы
   `df.get_for_resource` / `df.wait_for_resource` и старое ограничение cron-слотами (3).
   **Замысел пользователя (2026-11-23):** пытаемся запустить весь следующий уровень; при нехватке
   ресурсов остаются хвосты; на следующем уровне к ним возвращаемся; если точка следующего уровня
   уже доступна и её priority выше, чем у хвоста, — она идёт первой. Текущий walker этого не умеет:
   завершившаяся точка видит pending на своём уровне и не запускает следующую волну, а отложенные
   точки никто не подхватывает — реализовать возврат к хвостам с учётом priority вместе с лимитом
   (сюда же относится гейт `vw_ordr_max`).
3. **Довести легенду example до ума**: недостающие объекты
   `dwh.vw_main_dwh_payment -> dwh.dwh_payment`, `dwh.vw_dwh_debt -> dwh.dwh_debt` (+ `cond_col`),
   `dwh.vw_ams_collection_event -> dwh.ams_collection_event`.
4. **Переименовать схему `dwh` → `stdwh`.**
5. **Переименовать схему `df` → `ssdf`.**
6. **Починить гонку `id_batch = max+1`** при двух параллельных диспетчерах.
   Подход: блокировка вокруг выбора номера и вставки в `df.batch_log` —
   `pg_advisory_lock(hashtext('ssdf_batch_id'))` в обоих путях (Python и SQL), без изменения схемы.
   Альтернатива — sequence (но тогда оба пути должны использовать её, и в нумерации будут пропуски).
7. **`df.horizon`: реализовать функционал `id`** (`id`/`id_end` объявлены, но не используются;
   сейчас работает только `DTTM`). Для id-горизонта `df.exec_id` строит фильтр
   `cond_col between id and id_end` вместо дат.

## Кандидаты (на рассмотрение)

- **Судьба `_use_rep_dttm` / `--no-rep-dttm`.** Пользователь сомневается в нужности. Флаг не влияет
  на запись rep-дат (они пишутся всегда), только исключает watermarks из расчёта зависимостей.
  На полных прогонах от StrtF он ничего не меняет (всё и так в батче); работает лишь при частичных
  прогонах между батчами. Решить: оставить или убрать.
- **`exec_log.row_count = 0` у P-точек** (`GET DIAGNOSTICS ROW_COUNT` после `CALL` всегда 0) —
  починить или убрать смысл колонки.
- **Судьба SQL-пути исполнения** (`df.exec_flow` / `df.exec_batch_from_id` на pg_cron/dblink/dbms_lock):
  Python-диспетчер его дублирует. Если отказаться — pg_cron/pg_background/pg_dbms_lock
  уходят из требований.
- **Тесты покрывают только Python-путь**; SQL-путь проверялся вручную (уровень планирования).
  Если SQL-путь остаётся — добавить его тесты.
